# 传感器帧同步与稀疏碰撞事件

运行内核收到有效动作才推进物理 tick。每个物理帧的传感器收集都等待该帧的 CPU `sensor.other.imu` 心跳，以及配置开启的 RGB、BEV、LiDAR。IMU 始终启用，但只用于内部同步，不出现在策略观测中。`sensor_tick=0.0` 表示每个物理帧采样，避免小数间隔舍入导致隔帧。

帧收集按明确的 frame ID 汇合，旧帧、未来帧或上一回合的消息不能代替当前帧；缺帧在 `observations.sensor_timeout` 后报错。等待期间不额外 tick。传感器回调携带回合 generation；关闭后拒绝所有回调。初始化、正常动作和公共前缀重演使用相同的传感器汇合规则。

CARLA 的碰撞传感器是稀疏事件流：没有碰撞时不会发送“本帧零事件且发送完毕”消息。IMU 心跳也不证明独立碰撞流已经发送完成。因此，**有限时间等待不能数学上保证任意延迟的碰撞都已经到齐**。

当前采用明确、有界的处理规则：

1. 帧心跳及所需密集传感器到齐后，等待 `observations.collision_settle_seconds`（默认 0.002 秒，允许 0–0.1 秒）的墙钟时间，让常规延迟的碰撞进入当前物理帧。
2. 等待截止即封存该物理帧；`collect()`、`collisions` 读取和 `assert_healthy()` 都检查流健康。等待截止不延长仿真时长，也不会额外推进世界。
3. 运行内核在返回 reset/step 结果前调用 `commit(frame)`，再次检查并记录最后提交结果的帧。每个动作请求在推进前、每个物理 tick 开始前再次检查健康状态。
4. 后续若收到已经封存帧的碰撞，记录 `LateSensorEvent`。若当前转移还未返回，commit 或后续检查立即使其失败；若此前已经返回，下一次 preflight 明确报告受影响帧并终止该回合的有效采样。

迟到事件不加入正常碰撞列表，不在下一帧补记碰撞奖励，也不返回一个伪造的正常训练转移。异常信息包含 `sensor`、`event_frame`、`sealed_frame`、`published_frame` 和 `actor_id`，由环境故障响应传给客户端。外部数据工程需要据此丢弃/标记受影响转移；环境不会静默修改已经交付的历史数据。

`published_frame` 表示运行内核最后通过 commit 的结果帧；调用完成到 IPC 发布之间仍可能存在延迟，协议无法撤回客户端已经读取的结果。这是稀疏流缺少完成标记的实际限制，不能把 2 ms 的默认值解释为零迟到保证。需要评估目标机器与传感器组合的延迟分布，显式调整等待预算，并保留迟到故障统计。

关闭或切换世界时，先使该回合的碰撞屏障与密集帧队列失效，再停止并销毁该回合拥有的传感器。旧 generation 或关闭后的碰撞不污染新回合。碰撞收集、封存和 commit 使用同一个条件锁，消除这些操作之间的数据竞争。

无 CARLA 测试覆盖乱序/缺失/跨回合消息、无可选观测传感器时仍必须等待 IMU、有限窗口内碰撞、封存后但返回前迟到、已返回后迟到、关闭中唤醒和旧世界回调拒绝。它们验证软件语义，不证明真实 CARLA 的消息延迟分布。
